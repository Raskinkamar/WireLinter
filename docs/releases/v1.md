# Version 1 release readiness

This page records integration surfaces that are intentionally part of the first WireLinter release and the evidence required before their preview status can be promoted.

## Meta WhatsApp

Version 1 includes three separate Meta WhatsApp contracts because they represent materially different traffic and authentication surfaces:

- `meta-whatsapp-webhooks` — signed inbound WhatsApp webhook delivery;
- `meta-whatsapp-webhook-verification` — inbound GET subscription verification handshake;
- `meta-whatsapp-cloud-api` — outbound WhatsApp message requests through the Meta Graph API.

The v1 regression baseline is deliberately exact:

| Contract | Expected passing rules | Coverage |
| --- | ---: | --- |
| `meta-whatsapp-webhooks` | 6 | inbound direction, POST, JSON content type, `X-Hub-Signature-256`, WhatsApp object, acknowledgement status |
| `meta-whatsapp-webhook-verification` | 5 | GET, subscribe mode, verify token, challenge response, status |
| `meta-whatsapp-cloud-api` | 8 | outbound direction, Graph messages endpoint, POST, Bearer authorization, JSON content type, message payload, HTTP status, Graph semantic errors |

The automated regression suite also requires these negative cases:

- an incorrect demo app secret must fail `WL-META-WA-WEBHOOK-SIGNATURE-001` with a signature mismatch;
- an incorrect demo verify token must fail `WL-META-WA-VERIFY-TOKEN-001` with a secret mismatch;
- a Graph API `error` object must fail `WL-META-WA-CLOUD-GRAPH-ERROR-001` even when the transport status is HTTP 200.

All repository fixtures use synthetic or redacted values. Real Meta app secrets, verify tokens, access tokens, customer phone numbers, message contents, or other production credentials must not be committed as test evidence.

## Homologation evidence gate

The three Meta WhatsApp contracts remain `preview` until homologation evidence has been captured and reviewed. Before promoting them, capture one representative sanitized trace for each surface and lint it with the corresponding bundled contract.

Sanitization must preserve the evidence needed by the rule being tested. In particular, signature verification needs the exact raw request body and its matching sanitized test secret/signature pair; webhook verification needs exact query semantics; outbound API evidence must preserve the request shape and the relevant Graph response semantics. Do not keep a real credential merely to preserve fidelity: derive a safe fixture from the homologation shape instead.

For the initial v1 work, the pack definitions were functionally checked with an already built WireLinter binary on a host without a Go toolchain. The repository Go regression suite remains authoritative and must pass in CI before release.
